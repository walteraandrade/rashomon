# rashomon

Which words stick to a Brazilian political figure, across Bluesky, Google News, GDELT and RSS. Node + TypeScript, Hono API, PGlite database, SvelteKit (`adapter-static`, prerendered) front-end: pages in `web/routes`, modules in `src/ui`, assets in `public/`, built by `pnpm build` into `build/`.

## Commands

- `pnpm typecheck` runs `svelte-kit sync && tsc -p tsconfig.json && svelte-check --tsgo --tsconfig ./tsconfig.svelte.json`: plain `tsc` for the `.ts` tree, then `svelte-check` over `.svelte` files (`src/ui`, `web/routes`, `test/components`), which needs `tsconfig.svelte.json` (extends `.svelte-kit/tsconfig.json` for `$lib` and route types) and the `typescript@6` plus `@typescript/native` (TS 7) pair `svelte-check` requires. `pnpm test` runs `node --test` against an in-memory database, then `vitest run`: component specs (`test/components/*.spec.ts`, happy-dom) run only under vitest, `test/*.test.ts` only under `node --test`, so no `document` leaks into the latter. Both must pass before a PR.
- `pnpm build` is `vite build`: SvelteKit `adapter-static` prerenders `/`, `/como-ler` and `/sobre` into `build/` (gitignored), bundling the `src/ui` components through `web/routes/+page.svelte`. `pnpm test` never runs it.
- `pnpm materialize` writes the warm recortes' response bodies into the `warm_entries` table of the same database (`--if-stale`, `--dry-run`; needs an aggregate build, no token, no URL, and it opens `DATA_DIR` like `pnpm ingest`); run it after a manual `pnpm score`. The function reads that table with no setting at all.
- `pnpm dev` is Vite on 5173 with `/api` proxied to `PORT` (default 3210); `pnpm dev:api` is the Hono process (API only, Hono serves no HTML or `public/`). `pnpm ingest [source...]` collects. `pnpm reindex` recomputes terms and person matches from stored docs. Both end by rebuilding the graph aggregates; `pnpm aggregate` rebuilds them alone (after a `pnpm push`, for instance). `pnpm warm` asks the deployed site for the page's default recortes.
- `DATA_DIR` selects the PGlite directory (default `./data/pg`). `memory://` is an in-memory database and is what tests use.
- `DATABASE_URL` (or `POSTGRES_URL`) switches every command to a managed Postgres over `@effect/sql-pg`; that is how Vercel runs it (`api/index.ts`, `vercel.json`). `src/push.ts`'s one-shot copy still opens its own `pg.Pool`. `pnpm migrate` creates the schema there, `pnpm push` copies a local PGlite into it. Tests never set it.

## Hard constraints

- PGlite allows one process per data directory. Never run the server and an ingest/reindex on the same `DATA_DIR` at once. Agents working in parallel must each use their own `DATA_DIR`.
- Do not hit external APIs from tests. Collectors are integration code; test extraction and SQL against the fixture in `test/fixture.ts`.
- `seed.json` is the list of tracked people. Aliases match as whole words, case- and accent-insensitive. A one-word alias like "Leite" matches the beverage; prefer full names for common words. Alias words are excluded from the person's own terms. Longer aliases win: "Flávio Bolsonaro" tags Flávio only, never Jair's bare "Bolsonaro". A person's optional `exclude` list holds names that must not feed a bare alias ("Ciro Nogueira" for Ciro Gomes). Run `pnpm reindex` after editing it.
- A `phrase` term is several words as one: a capitalized run (`Alexandre de Moraes`) or a collocation the corpus shows sticking together (`primeiro turno`). The collocation lexicon lives in `phrases` and is rebuilt only by `pnpm reindex`, which therefore reads the corpus twice; `pnpm ingest` loads that lexicon and never adds to it. A phrase replaces the word occurrences it covers, positionally: a word only leaves a doc when every occurrence of it there is inside a phrase, so a word's count means "docs where it appears at least once outside every phrase". A pair touching a tracked person's alias word never enters the lexicon, or a phrase the name filter hides would delete its words with nothing in their place. A phrase carrying one of a person's own name words is dropped from that person's graph.
- `kind` on `/graph`, `/docs`, `/rising`, `/timeline` and `/week` takes a comma-separated list, like `source`; `query.ts`'s `KINDS` now also accepts `org` (GDELT-only, read from a gkg row's `V1Organizations` column — GDELT's theme codes are still never collected or served). `web/routes/+page.svelte` sends `word,hashtag,phrase,org` (`ATLAS_KINDS` in `api.ts`), the full set.
- Tone exists only on GDELT (`gkg`, `gdelt`) docs. Every other source has `tone = null`. Never invent tone for them. Reach (a Bluesky post's like/repost/reply/quote counts, `docs.reach_*`, served as `reach` on `/graph` and `/rising`) exists only on Bluesky docs; every other source has `reach` null, never invented.
- `sort=pmi` orders by `pmi * ln(1 + count)`, on purpose, so rare terms do not dominate. Do not change without a test.
- Bluesky blocks unauthenticated bursts. Keep the pacing in `src/collectors/bluesky.ts`; login via `BSKY_HANDLE` and `BSKY_APP_PASSWORD` is the sanctioned path. Never write credentials to the repo.

## Layout

- `src/types.ts`'s `Collector = (persons) => Effect.Effect<RawDoc[], CollectorError, HttpClient.HttpClient | SqlClient.SqlClient>`; `collectors/index.ts` registers each module's own `collect` Effect directly, and no collector module exports a Promise-returning wrapper around it. `CollectorError` is an explicit union of `http.ts`'s shared errors plus each collector's own tagged class (`BlueskyError`, `GkgError`, `RssError`; gdelt/camara/senado's `collect` never lets a failure escape, typed as `never`) — a new collector error type is added here by hand, never inferred.
- `src/http.ts` is the collector layer's HTTP boundary (Effect 4 RC, `effect@4.0.0-rc.117`, pinned exact because the RC still renames APIs between builds; `node_modules/effect/AGENTS.md` and `node_modules/effect/ai-docs/` are the reference for this RC's own API, read them before writing or changing Effect code here): `getBytes` is one capped, timed GET on Effect's `HttpClient` (`limit`/`timeoutMs` default to `MAX_RESPONSE_BYTES`/`REQUEST_TIMEOUT_MS`, the byte cap and the wall-clock cap always travelling together), `fetchClient` the only layer (global fetch, trace-header propagation off); nothing in `src/` turns a collector Effect into a Promise any more, `ingest.ts` provides the layers at its own entrypoint. `gkg.ts`'s zip download carries its own ceiling, `GKG_DOWNLOAD_TIMEOUT_MS` (300 000 ms), passed as `getBytes`'s third argument, distinct from every other collector's default `REQUEST_TIMEOUT_MS` (45 s) — a slot is too large for the ceiling sized for small JSON endpoints; a per-slot failure (oversize or a timeout) is caught inside `collect` so it costs only that slot, never the run. `camara` and `gdelt` keep their hand-measured retry counts and backoff formulas, now as typed, TestClock-driven Effects rather than recursive `setTimeout`-free Promises. Tests drive every collector through `test/effect.ts`: a stub `fetch` handed to `FetchHttpClient.Fetch`, `TestClock` for every pause and timeout, `TestConsole` for the log lines, so a 45 s timeout or a 5-minute download costs the suite nothing.
- `src/ingest.ts`'s `ingest(persons, names, options)` is the orchestration Effect: `migrate`, `pruneRemoved`, `upsertPersons`, `loadPhrases`, `pageviews`, `retention`, `docCount`, `analyzeAfterWrite`, `buildGraphAggregates` and `analyzeTables` are every call whose failure fails the whole run, each as a typed `IngestFailure({ stage })`. Every stage but `buildGraphAggregates` (still `Effect.tryPromise`, out of scope so far) runs as a native Effect `yield*`, mapped with `Effect.mapError` into that `IngestFailure` — none of them goes through `Effect.promise`/`Effect.tryPromise`, so a rejection can never resume as a `die` that bypasses a caller's `Effect.catchTag`. A collector's failure or an unknown source name costs that source alone (`Effect.exit`, logged, `docs = []`), and `insertDocs` (never rejects by construction, `Effect.orDie` enforcing it) still runs for it. `pageviews` (Wikipedia attention, `src/collectors/pageviews.ts`) is its own stage, run once after the doc-collector loop on every `pnpm ingest` regardless of which sources were named, never through `runSource`/`registry`/`defaultSources`; a person's own fetch failure is isolated and logged inside the stage, never fails the run, but the stage's own SQL write failing does, as `IngestFailure({ stage: 'pageviews' })`. `retention` (`store.ts`'s `trimOlderThan`, one `delete from docs` counted in its own statement) runs right after `pageviews`, before `docCount`, and deletes every doc older than `Math.max(...DAYS)` days (`query.ts`'s `DAYS`, 7 and 21: the widest window and the horizon are one constant, so retention keeps 21 days; issue #313; `doc_persons`/`doc_terms`/`doc_testimony`/`doc_candidates` cascade, `person_attention` and `terms` are not trimmed, and `IngestReport.deleted` carries the count); `migrate()` also drops the rows of every retired window, `db.ts`'s `RETIRED_WINDOW_DAYS` (30, 60 and 365, a literal list that never intersects `DAYS`), from every windowed table. `SourceResult` carries `dropped` (the docs the store refused for naming nobody tracked; 0 for a failed or unknown source) apart from `written`, the log line is `[name] fetched F, new W, dropped D` plus `, enriched E`/`, failed X` only when non-zero, and `analyzeAfterWrite` is fed `written` alone. `IngestOptions` holds only `collectors`, overriding the real registry per source; a stage failure is reached only through the ambient `SqlClient.SqlClient`, which `test/ingest.test.ts` makes fail with `test/effect.ts`'s `failingSql(client, match)`, a proxy over the real client that fails only the one statement `match` recognizes — never a per-stage option. `Effect.forEach(names, …, { concurrency: 1 })` keeps sources sequential, Bluesky-last order intact. The CLI entrypoint provides `HttpClient` (`fetchClient`) and `SqlClient` (`db.ts`'s own running connection, fetched once via `runSql(SqlClient.SqlClient)` — never a second one on the same `DATA_DIR`) and sets `process.exitCode = 1`, never `process.exit()`, on a failed run.
- `src/extract.ts` normalization, hashtags, words, phrases, stopwords, person matching.
- `src/phrases.ts` the collocation lexicon: staging every adjacent word pair, the count/stickiness floors, loading it back. `loadPhrases` is Effect-native (`SqlClient.SqlClient`, `SqlError`); `loadPhrasesP` is its `runSql(...)` adapter. `buildPhrases`, `stagePhrases`, `resetPhraseStage` stay Promise-only, `reindex.ts`'s own.
- `src/db.ts` picks the `SqlClient` layer by `DATABASE_URL`/`POSTGRES_URL` (`@effect/sql-pg` when set, `@effect/sql-pglite` at `DATA_DIR` otherwise; `memory://` for tests) and wraps it in the `db: { query, exec, close }` Promise adapter every other module calls. `migrate`, `analyzeTables`, `analyzeAfterWrite` and `docCount` are Effect-native, requiring `SqlClient.SqlClient` and failing with `SqlError`; `migrateP`, `analyzeTablesP`, `analyzeAfterWriteP` are their one-line `runSql(...)` Promise adapters (`docCount` has none — `ingest.ts` is its only caller). `poolConfig` stays pure/synchronous and, besides `@effect/sql-pg`'s own `PgPoolConfig` fields, still returns `pg`'s `connectionString`/`connectionTimeoutMillis` so `src/push.ts`'s own `pg.Pool` keeps working unchanged. `runInTransaction` (re-exported by `store.ts` as `inTransaction`) is the only way a transaction opens: always through `inTransaction` at a Promise call site or `sql.withTransaction` at an Effect one, never a raw `begin`/`commit`/`rollback` string; a nested `inTransaction` becomes a savepoint. `runSql` opens none — it is the Effect-to-Promise runner every `P`-suffixed adapter goes through, joining whatever transaction (if any) is already open. A module-private `AsyncLocalStorage` (shared with `store.ts`) is what lets a plain `db.query`/`db.exec` call made inside an open `inTransaction` join it. Under `PERF=1`, `DbLayer` itself wraps the resolved `SqlClient`'s `unsafe` to time and count every statement — the one point every write, whether through `db.query`/`db.exec` or a bare Effect writer's own `sql.unsafe`, passes through — so `db`'s own `query`/`exec` are never separately wrapped (that would double-count).
- `terms (id, term, kind)` (unique on `(kind, term)`) is the vocabulary and `doc_terms (doc_id, term_id)` references it (issue #252; `docs/operations.md`, "The term dictionary"). Every builder that reads `doc_terms` groups and joins on `term_id` and reaches `terms` only for text; no `order by` or tie-break ever uses an id, since ids follow insertion order and `pnpm reindex` renumbers them (it truncates `terms` with the rows it rebuilds). `graph_terms`, `term_communities` and `term_links` stay text-keyed, and `graph_terms_all` (temp) is keyed `(days, source, term_id)`. `migrate()` converts a legacy `(doc_id, term, kind)` `doc_terms` in place in one transaction, and a production deploy of that change pauses `ingest.yml` until `pnpm migrate` has run. A test or a script that writes a `doc_terms` row goes through `test/fixture.ts`'s `insertDocTerm` (the writer's own statement), never a raw insert.
- `doc_tone (doc_id, tone)` holds exactly the docs whose `docs.tone` is not null (issue #272; `docs/operations.md`, "The tone side table"): `termCounts` and `aggregate.ts`'s `personTermsQuery` read tone from it at the document level (`reach`, `docs.reach_reposts`, is read in that same per-document subselect, and `docs` is joined there only when the statement serves `reach`; never once per `doc_terms` row), everything else (`/docs`, `/sources`, `/tone`, `export-docs`) still reads `docs.tone`. Written only by `UPSERT_DOCS_SQL`, backfilled once by `migrate`, pushed from `docs`, never inserted by the bench seed. A production deploy of that change pauses `ingest.yml` and runs `pnpm migrate` from the PR branch first.
- `src/store.ts` inserts docs and persons (shared by ingest and reindex), and keeps only docs that name a tracked person: `writeBatch` matches each doc's truncated text once (`personsMentioned`, handed on to `derive`, never recomputed) and drops a doc with no match before any statement, so a dropped doc leaves no `docs`, `doc_tone`, `doc_candidates` or `doc_testimony` row and `writeBatch` returns `{ written, enriched, dropped }` (`InsertTotals` adds `failed`). `extraNames` and `extraTerms` never make a doc tracked, each occurrence of a repeated uri is judged alone, and a stored tracked doc re-fetched with a text naming nobody is dropped, its row untouched. `pnpm reindex` reads stored docs only, so it neither recovers a dropped doc nor deletes one that stopped matching; `graph_scopes.docs` equals `graph_scopes.tracked`; a test that needs a stored doc naming nobody writes it with `test/fixture.ts`'s `insertOrphanDoc`. Each writer (`pruneRemoved`, `upsertPersons`, `writeDerived`, `insertDoc`, `insertDocs`) has one Effect implementation, requiring `SqlClient.SqlClient` and failing with `SqlError` under its bare name, so a caller can `Effect.catchTag` a typed `SqlError` instead of catching a flattened Promise rejection; a caller outside the Effect world (`reindex.ts`, `score.ts`, `server.ts`, `test/fixture.ts`, …) imports the one-line `P`-suffixed Promise adapter (`runSql(<name>(...))`) instead.
- `src/aggregate.ts` builds `graph_scopes` and `graph_terms`: per window (`query.ts`'s `DAYS`, 7 and 21) and single source (its `SOURCES` + `all`), the counts `graphFastQuery` reads by primary key so the `/graph` statement never scans the corpus on a MISS; `graph_terms` holds not every term but, per `(source, kind)`, the top `TOP` (`LIMITS`' largest) of each ordering the route can request — by count, and by `pmi * ln(1 + count)` once per `min` in `MINS` — plus the signature's five, so every `sort`/`min`/`kind`/`limit` still reads exactly the live answer while the table stops growing with the corpus (the full list reached 544 MB and filled the production disk); `testimony=1` still runs live. `GET /api/compare` (`compareFor`) and `GET /api/people/:id/lenses` (`lensesFor`, `src/graph.ts`, issue #247) read `graph_scopes`/`graph_terms` directly on a precomputable recorte instead of scanning `doc_terms` — no table of their own, so a database with a `/graph` build already answers them fast, no rebuild and no extra migration. A person's own name words are still excluded from `graph_terms` at build time, same as `/graph`'s own nodes: `/compare` still finds a person's own name through the *other* person's own vocabulary when it ranks there, but `/lenses`' single-person union has no other side to pull one in from, so a person's own name word never appears on the precomputed `/lenses` ruler at all — only the live path still shows it. `term_links` (`days, source, person_id, a, b` primary key, issue #251) exists but the build no longer persists into it: it grew to 479.5 MB on the production Supabase instance on 2026-09-29, filled the disk and put the database read-only. Each window build only `delete`s that window's rows (so a stale row from an older build never serves), and `/graph`'s links run live (`linksQuery`) off the warm set; `graphFor`'s `linksFor` still probes the empty table first (`linksFastQuery`, one index lookup) and falls back to live on zero rows. A future smaller linkable set needs its own spec. It stays in `ANALYZED_TABLES` and `POST_BUILD_ANALYZED` but never in `AGGREGATE_TABLES`/`hasGraphAggregates`, same as `term_communities`. The PMI denominator lives in `graph_terms_all`, a `create temp table ... on commit drop` built once per window inside that window's own transaction (issue #203) — never a persisted table, so it costs no disk and needs no `analyze`. `pnpm aggregate` runs it (`--if-missing` skips a database that already has a build); `pnpm ingest` and `pnpm reindex` call it last and analyze the persisted tables the build itself wrote, `POST_BUILD_ANALYZED` (`graph_scopes`, `graph_terms`, `term_communities`, `term_links`, `outlet_fields`, `outlet_neighbors`) — the builder analyzes only `graph_terms_all` and `graph_terms` mid-window, for its own later statements, and opens each window transaction with `set local work_mem = '128MB'` (issue #250; never copy that into `poolConfig`). One transaction per window; scopes and terms come from the same person list, so a scope row always has its terms. `graphFor` tries the fast query when `precomputable(q)` (a window in `DAYS`, no domain, no lean, one source, `country=br`; the build holds only that universe, so `.pt` docs never enter it and `country=pt`/`all` always run live) and falls back to the live statement on zero rows; `test/aggregate.test.ts` pins that both render identical output on every recorte of the fixture and that only the window edge (build time, not request time) tells them apart. A change to `graphQuery`'s counting rules is a change to `aggregate.ts` too. The pmi ordering, the signature floor, the own-name filter and the country predicate both files share live in `src/scoring.ts`, not repeated here or in `graph.ts`. A third table, `term_communities` (`days, source, person_id, term, kind` primary key), is written last inside the same window transaction, right after that window's `personTermsQuery` calls: for every `(days, source, person)` `graph_terms` was just filled for, it re-derives the co-occurrence edges over that scope's kept `(term, kind)` set (each doc's own kept term ids paired with themselves via `unnest`, against `graph_terms` instead of a request's live `ids`) and hands them to `src/communities.ts`'s pure Louvain wrapper, a fixed seed so one edge list always partitions the same way within one library version. It is in `ANALYZED_TABLES` (`src/db.ts`) but deliberately **not** in `AGGREGATE_TABLES`/`hasGraphAggregates` — a community build lagging behind `graph_terms`/`graph_scopes` must never look like a missing aggregate build, or `pnpm aggregate --if-missing` would re-run the whole window build just to catch communities up; a stale or missing community build degrades a node's `community` to `null` instead.
- `src/communities.ts` pure graph metrics over co-occurrence edges: `communities(edges, seed)` takes `{ a, b, count }` co-occurrence edges and a fixed seed and returns a `Map<string, number>` of node id to community number, built on `graphology` + `graphology-communities-louvain` (both pinned exact, no `^`/`~`, matching the `effect@4.0.0-rc.117` precedent — Louvain's result is not stable across library versions). No import from `db.ts`, `store.ts`, `aggregate.ts` or any Effect/SQL module; only `src/aggregate.ts` (for `communities` and `neighbors`) and `src/graph.ts` (for `betweenness`) import it, so `graphology` is in the server's import graph but must never reach `src/ui/*` (`pnpm build`'s bundle never grows to include it). `betweenness(edges)` (issue #219) is the same pattern, unnormalised, built on `graphology-metrics` (pinned exact too), for `/compare` and `/lenses`'s `bridges=1`. `neighbors(sets, topK)` (issue #218) is plain Jaccard between domains' top-term sets, no graphology: `aggregate.ts` feeds it each `(days, person)`'s domains (at least 3 docs, top 40 terms, `source=all`), keeps the top 5 per domain in `outlet_neighbors` and hands every non-zero pair, once and undirected (the top-5 cap never trims Louvain's graph), to `communities` for `outlet_fields`, both written inside the window transaction and, like `term_communities`, analyzed after the build but kept out of `AGGREGATE_TABLES`; `/sources` rows read them as `field` (`null` when unbuilt) and `neighbors` (`[]`).
- `term_weeks (person_id, term, kind, week, count, c_t)` (primary key on the first four, the person FK cascades; issue #215) is the one persisted history, not a cache: `src/aggregate.ts`'s `buildTermWeeks(persons, now = new Date(), top = TERM_WEEKS_TOP)`, the last step of `buildGraphAggregates`, keeps per person the top 50 (`TERM_WEEKS_TOP`) of the current and previous BRT Monday week, `count >= TERM_WEEKS_MIN` (2), ranked `pmi * ln(1 + count)` against a `c_t` over the widest `DAYS` window (`term_weeks_universe`, a temp table). One injected `now` is bound once and every statement derives its weeks from it (none reads SQL `now()`, `current_date` or `windowScope`); it deletes then inserts only `cur` and `prev`, never an older week, so the size stays bounded (lifting the bound needs its own spec, #267). In `ANALYZED_TABLES`, `POST_BUILD_ANALYZED` and `SIZE_TABLES`, not in `AGGREGATE_TABLES` and not in `push.ts`'s `tables`. `src/graph.ts`'s `persistence`/`persistenceFirstWeek` builders (`queries`/`statements`) and `persistenceFor(person, q, now)` read it for `GET /api/people/:id/persistence`; `persistenceStats(counts)` is the pure streak/half-life. `week=` on `/docs` (`docsWeek`, `query.ts`'s `keepWeek`) renders no text when empty so the pinned `docs`/`docsCount` statements stay byte-identical, and a resolved `day` wins over it in the parser.
- `src/scoring.ts` the fragments `graph.ts` and `aggregate.ts` both build SQL around: `pmiLog2` (the raw `ln((c_pt * n) / (np * c_t)) / ln(2)`; `graphFast` and `aggregate.ts`'s `personTermsQuery` keep their own `::float8` copies and do not call it, the fast statement because its text is pinned), `pmiRank` (`pmi * ln(1 + count)`), `sortKey` (branches on `sort=pmi` between `pmiRank` and the bare count), `signatureFloor` (`greatest(3, about * 0.05)`) and `isName` (a term is, or a phrase carries, one of a person's own name words — subsumes the old `namePhrase`) and `countryFilter` (the `country` scope predicate; `aggregate.ts` bakes in its `'br'` arm), plus `outletDomain`: a Bluesky doc's `domain` is its author's handle, an account rather than a veículo, so `sourcesQuery`, `testimonyScopeCte` and `agendaQuery` all read it through this fragment as null and no handle ever ranks among outlets (a `domain=<handle>` filter on `/docs` or a `domain:<handle>` lens still matches the stored value). Pure `Sql`-returning functions built only with `sql.ts`'s tag; imports nothing from `graph.ts` or `aggregate.ts`, so both import it and neither cycles back.
- `scripts/prod-explain.ts` is the timing source: read-only production `EXPLAIN (ANALYZE, BUFFERS)` (each case twice, `cold` then `warm`, inside `begin transaction read only` ... `rollback`) plus `pg_stat_statements`, refused inside the aggregate build window unless `--force`, never run from CI or tests (`docs/operations.md`, "Timing source"). The PGlite harness under `scripts/bench` decides row equivalence and plan shape only; `compare.ts` never rejects on speed. `test/prod-explain.test.ts` drives `run` with a recording fake client, never a network connection.
- `src/warmstore.ts` and `src/materialize.ts` are the warm store (`docs/operations.md`, "The warm store"): `warm_entries (pathname primary key, person_id references persons on delete cascade, body)` holds one row per recorte, `body` being `<graph_scopes.built_at::text>\n<response JSON>`; `warmRecortes` derives one entry per `warmPaths` path (key `sha256` of the route and the whole parser output, pathname `warm/v1/<person>/<route>/<key>.json`, only a primary key now), `lookup` serves a row only when its first line equals the scope's current `graph_scopes.built_at::text` (`x-warm-store: hit|stale|miss` on every lookup-eligible request, `x-warm-store-only: 1` turns a miss into a 503; any failure, a missing table included, is a `miss`, with no read timeout), and `materialize` builds each body with `graphFor(person, q, linksOf)`, `sourcesFor` or `testimonyFor`, `linksOf` slicing `aggregate.ts`'s `communityEdges` so a stored `/graph`'s links never run `linksQuery`. `pgWarmStore` is the one reader and writer (module-level `db.query`, so `recordStatements` sees it; `get` is `select body from warm_entries where pathname = $1`, `put` an upsert), `memoryWarmStore` serves `--dry-run`, and `server.ts`'s `setWarmStore(store | null)` is a test seam only (`null` disables lookups). `WarmReader = { get(pathname) }`, `WarmWriter = { put(recorte, text) }`. `materialize` never deletes: rows whose key a parser or `TESTIMONY_REVISION` change retired are harmless orphans, cleared by hand. The table is not in `ANALYZED_TABLES`, `AGGREGATE_TABLES` or `push.ts`'s `tables` (`pnpm materialize` rebuilds it, `pnpm push` does not copy it); it is in `SIZE_TABLES`. `main(argv, deps)` (`writer`, `reader`, `log`) never migrates.
- `src/warm.ts` asks the deployed site for the page's own recortes (`warmPaths`, built with `src/ui/api.ts`'s functions so the cache key matches) after every ingest and every production deploy. No network in tests: `warm` takes its `fetch`.
- `src/jev.ts` the Jev shadow review `.github/workflows/jev-review.yml` runs as `pnpm jev-review` on every PR (docs/factory.md, "Jev shadow review"): pure parts (`findSpec`, `parseCriteria`, `closedIssue`, `buildQuestions`, `buildRequest`, `parseAnswers`, `overCap`, `renderComment`) plus `upsertComment` and `main`, whose `fetch`, `git` and artifact writer are injected, so no test touches the network or a process. The reference lives in `docs/`: `api.md` (routes), `sources.md` (collectors and `seed.json`), `terms.md` (PMI, phrases, candidates, lean, tone), `testimony.md` (kikori), `operations.md` (env, deploy, writes, indexes, benchmarks, caching). A change documents itself in the matching page, not by growing the README back: a layout or constraint every agent must know goes in `CLAUDE.md`, a change to the factory pipeline itself in `docs/factory.md`. `DESIGN.md` and `PRODUCT.md` at the repo root are the visual and product spec (impeccable); they are not the `docs/` reference.
- Import direction is one way and acyclic: `format.ts` ← `layout.ts`, `combobox.ts`, `docs-paint.ts`, `compare-model.ts`, `butterfly-model.ts`, `strip-model.ts`, `measure.ts` ← the `.svelte.ts` state modules (`docs-card.svelte.ts` imports `docs-paint.ts`, `api.ts`, `perf.ts`, `state.ts`; `figure.svelte.ts` imports `docs-card.svelte.ts`) ← the components, with `api.ts`, `state.ts` and `perf.ts` at the bottom (`state.ts` imports `perf.ts` for the memo-hit mark). `atlas-model.ts` imports only `api.ts` and `format.ts`; `Atlas.svelte` imports exactly `api.ts`, `atlas-model.ts`, `boot.svelte.ts`, `docs-card.svelte.ts`, `figure.svelte.ts`, `format.ts`, `layout.ts`, `measure.ts` and `seed.ts`. `Butterfly.svelte` imports only `format.ts` and the type from `butterfly-model.ts`; `Dumbbell.svelte` imports only `format.ts`; `Rising.svelte` imports exactly `Dumbbell.svelte`, `api.ts`, `boot.svelte.ts`, `docs-card.svelte.ts`, `figure.svelte.ts`, `format.ts` and `seed.ts`; `Compare.svelte` imports exactly `Butterfly.svelte`, `Combobox.svelte`, `api.ts`, `boot.svelte.ts`, `butterfly-model.ts`, `compare-model.ts`, `docs-card.svelte.ts`, `figure.svelte.ts`, `format.ts` and `seed.ts`. `test/invariants.test.ts` enforces it.
- `.svelte` files under `src/ui` and `web/` follow the module rules, checked in `test/invariants.test.ts`: import only from `src/ui` (no `src/*.ts` elsewhere, never `graphology`), no `innerHTML`, no `{@html}`, no `<style>` block or `style=` attribute (`style:--name` only), no px `font-size`. `src/ui/Proof.svelte` is the harness fixture (`test/components/Proof.spec.ts`, plus `Proof.server.spec.ts` under a node environment for `svelte/server`), mounted by no route. A component spec mounts with `mount()`, dispatches a real bubbling event and calls `flushSync()`.
- The front end is TypeScript like the rest of `src/`, so `pnpm typecheck` covers `src/ui` with no `allowJs`/`checkJs` escape hatch. Modules import each other with `.js` specifiers (`./format.js` resolves to `format.ts`), which is what NodeNext, tsx and Vite all agree on. A new module or parameter needs its types, or `tsc` fails.
- `test/` node:test suites. `test/fixture.ts` seeds two people and six docs; extend it rather than creating ad-hoc data. A DOM-dependent case is a happy-dom component spec under `test/components/`, never a hand-rolled `document`. A test asserts on output or behaviour; a test may read a module's source only to check a repo-wide invariant listed in `test/invariants.test.ts`, never to check that one function calls another.
- Front-end behaviour is tested by mounting components, never by grepping `web/routes/+page.svelte` for JavaScript. A criterion about a click or keystroke goes through a component spec in `test/components` that mounts the component and dispatches a real event; a criterion about markup goes through that spec or the prerendered page (`test/pages.ts`).

## Style

- Code, comments, commits, branches, PR titles in English. UI copy in pt-BR.
- Functional style, small pure functions, no classes, except in exactly two shapes: a `Data.TaggedError` (a typed failure, e.g. `ResponseTooLarge`, `BlueskyError`) and a `Context.Service` (an Effect service definition). Nowhere else. Comments only when the why is not obvious.
- A comment states the constraint; history lives in git and docs/.
- Commit messages short and imperative. Branch names `feat/ | fix/ | chore/ | refactor/ | docs/ | test/` + short kebab slug.
- Keep the API contract stable: `GET /api/people`, `GET /api/people/:id/graph`, `GET /api/people/:id/sources`. New capabilities are new routes or new optional query parameters, never breaking changes to existing fields. `testimony=1` on `/graph` is one such parameter: off, the response is unchanged.

## Factory

Feature work goes through the pipeline in `docs/factory.md`: `spec` workflow → human adds `spec-approved` → `build` workflow → PR → human review. Roles live in `.claude/agents/`; whoever builds never validates. Builders work in `../rashomon-<slug>` worktrees, never on the main checkout.
